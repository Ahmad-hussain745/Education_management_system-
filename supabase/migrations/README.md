# Migrations — naming convention and the 0059 collision

## What was wrong

The zip contained two migrations both numbered `0059`:
- `0059_fix_monthly_closing_uniqueness.sql`
- `0059_student_contact_address.sql`

Two independent lines of work each incremented from `0058` without checking
against the other, so both landed on `0059`. Supabase's migration history
(`supabase_migrations.schema_migrations`) tracks applied migrations by the
version string parsed from the filename prefix — it expects that prefix to
be unique. Two files sharing one prefix is a real collision, not just an
untidy filename: depending on the tool/ordering involved, it can mean one
of the two never gets recorded as applied at all, or the two get applied in
whatever order the filesystem happens to list them rather than the order
either was actually written in.

## What was fixed, and how the choice was made

`0059_student_contact_address.sql` was renamed to
`20260919145113_student_contact_address.sql` — moved to *after* `0060`,
using the timestamp convention below. `0059_fix_monthly_closing_uniqueness.sql`
was left exactly where it was.

That choice was checked, not arbitrary: the two migrations touch entirely
unrelated tables (`monthly_closing` vs. `students.address`), so there is no
dependency in either direction — moving either one anywhere relative to the
other is safe on its own logical merits. Given that, the address column
(a small, additive, purely-cosmetic change) was the one moved later, past
`0060`, rather than renumbering the bug-fix migration or disturbing
anything already between `0058` and `0060`.

**This zip's own migrations were run end-to-end against a genuinely fresh
local Postgres 16 database as part of fixing this** (see Phase 33's testing
work) — all 61, in filename-sort order, with no errors and no manual
intervention. That confirms the fix is *internally* consistent. It does
**not** confirm what your actual Supabase project has or hasn't already
applied — that can only be checked against your specific project, which
this environment has no access to.

## Before you push this: check your project first

Do not apply this zip's migrations directory blindly if you have already
run `supabase db push` (or applied migrations by hand) against a real
project at any point. Run, from your project directory:

```
npx supabase migration list
```

This prints a table with a `Local` column (migrations present in your
`supabase/migrations/` folder) and a `Remote` column (what your project's
`schema_migrations` history actually recorded as applied). Specifically
check the `0059` row(s):

- **If your remote history shows a `0059` entry and its content, if you
  can tell from context, is the monthly-closing fix** — this zip's layout
  already matches that: nothing further to do, push normally.
- **If your remote history instead shows `0059` corresponding to the
  student-contact-address change** — this zip's renumbering guessed
  wrong for your specific history. Don't push this zip's migrations
  directory as-is. Instead, locally: rename
  `0059_fix_monthly_closing_uniqueness.sql` to a new timestamped name
  (using `supabase migration new`, below, or by hand) and leave
  `20260919145113_student_contact_address.sql`'s content as the one that
  keeps the `0059` slot your project already recorded, matching what's
  actually deployed. Then push.
- **If your remote history shows no `0059` at all (or you haven't run
  `supabase db push` against this project before)** — this is the common
  case for a project still in development, and this zip's layout is
  already correct; push normally.

The reason this matters, concretely: if you rename a migration file whose
version was already recorded as applied, Supabase sees what looks like a
brand-new, never-applied migration under the new name and will try to run
it again on your next push — for these two migrations specifically that
would be harmless (both use `if exists`/`if not exists` guards, so
re-running is a no-op), but that's a property of these two migrations, not
something to rely on in general. Checking first, rather than assuming it's
safe, is the actual point of running `migration list` before pushing.

## Naming convention from here on

Every new migration should use Supabase's timestamp-based format —
`YYYYMMDDHHMMSS_description.sql` — generated by:

```
npx supabase migration new feature_name
```

rather than manually incrementing a plain number
(`0061_feature.sql`, `0062_feature.sql`, ...). A generated timestamp can't
collide with anything else being worked on in parallel the way two people
(or two sessions) both guessing "the next number" can. The existing
`0001`–`0060` files are left as they are — renumbering 60 already-numbered
migrations into timestamps would be a much larger, riskier mass-rename for
no real benefit, since their relative order is already unambiguous and
none of them collide with each other. Only new migrations from this point
forward use the timestamp format; `20260919145113_student_contact_address.sql`
is the first one.
